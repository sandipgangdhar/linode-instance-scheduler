Linode Instance Scheduler: The Definitive Guide

Part 0

Why This Exists

The billing fact that makes this tool necessary, who it's built for, and the single sentence that describes what it actually does.

0.1 The Problem: A Stopped Instance Still Bills

On most clouds, "stop the server" and "stop paying for it" are the same action. On Linode, they are not. A powered-off Compute Instance continues to reserve its RAM, CPU, and network capacity, and continues to bill at exactly the same hourly rate as a running one. The only action that actually stops compute billing is fully deleting the instance — not shutting it down, not powering it off, deleting it.

That single fact is the entire reason this tool exists. A team that wants to run a development environment only during business hours, a batch-processing fleet only overnight, or a demo environment only when someone is actually using it has no native "pause billing" button to press. The only way to genuinely stop paying is to delete the instance — and deleting an instance normally means losing it: its identity, its configuration, and, if the OS lives on local disk the way a freshly-deployed instance normally does, its data.

Instance Scheduler automates a full delete/recreate cycle and makes it behave like an ordinary stop/start, by making sure everything that makes an instance recognizably "the same machine" survives the cycle on resources that are never touched by the delete: its OS disk, any additional data volumes, its public IP address, and its VPC/VLAN network identity. From the outside, an instance managed by this tool looks like it has a stop button and a start button. Underneath, "stop" deletes it and "start" recreates it from exactly what was there before — and only while it's actually deleted does the compute billing genuinely stop.

0.2 Who This Is For

Any workload that doesn't need to run around the clock is a candidate: development and staging environments used on business hours only, CI/build agents that sit idle most of the day, demo or training environments spun up for specific sessions, batch or overnight-only processing fleets, and standby/failover nodes that only need to exist when actually promoted into service. The common shape is the same in every case — a real, persistent machine identity (data, network address, configuration) that only needs to be *running* some of the time.

It is not a fit for anything that needs to stay reachable continuously, or that can't tolerate the several-minutes-long window a full recreate cycle takes. A production database serving live traffic around the clock gets no benefit from this tool; a dev database that's only queried during working hours does.

0.3 The Core Mechanism, in One Picture

Every instance this tool manages has two states in its own registry: running (a real Linode instance currently exists) and stopped (it doesn't — and nothing is billing for compute). Moving between them is always the same sequence:

STOP START ──── ───── 1. Re-capture current identity 1. Create a new Linode instance (network config, tags, label, in the same region/plan data-volume layout, SSH keys) 2. Detach data volume(s) 2. Reproduce network config exactly (confirmed detached before (legacy or new interface model, continuing) VPC/VLAN addresses, reserved IP) 3. Delete the Linode instance 3. Attach OS volume + data volumes — compute billing stops here in their original device order 4. Inject the correct network Reserved IP: stays reserved configuration at boot time OS volume: untouched, independent 5. Boot, then verify real network Data volumes: untouched, independent reachability — not just that VPC / VLAN: independent resources, the API reports "running" simply not attached to anything right now
Fig. 0.1 — what a managed stop/start cycle actually does underneath

Nothing about this is exotic Linode functionality — every step is an ordinary, documented API call. What the tool provides is doing all of it correctly, in the right order, every single time, with the exact configuration re-applied identically on every cycle, and a real health check before ever reporting success. Part I explains why each of those steps exists and what would break without it.

Part I

How It Works

What survives a delete/recreate cycle and why, the two Linode networking models this tool has to account for, and the network re-injection mechanism that keeps a recreated instance reachable at the same address every time.

1.1 What Survives, and Why

A delete/recreate cycle only works as a stand-in for stop/start because four kinds of resources are independent of the Compute Instance's own lifecycle on Linode — deleting the instance never touches them.

Storage

Block Storage volumes

A volume is a separate resource from any instance, billed separately (a small per-GB/month rate, far below compute pricing) and completely unaffected by deleting the instance it happens to be attached to. This is why the OS itself has to live on a Block Storage volume, not local disk — see 1.2.

Networking

Reserved public IP

An ordinary instance's public IP returns to Linode's shared pool the moment the instance is deleted. A reserved IP is a standalone resource you own independently — it stays assigned to your account, in its original region, and can be attached to a newly created instance. It carries a small charge while unattached, and is permanently locked to the region it was first reserved in.

Networking

VPC and VLAN identity

A VPC subnet and a VLAN label are both persistent, independent resources — not tied to any one instance's lifecycle. Re-attaching a recreated instance to the same VPC subnet or VLAN, with the same internal address, requires no special preservation step; the resources themselves were never going anywhere.

Metadata

Label, tags, plan, firewall

None of these live on the instance in a way that survives deletion on their own — the tool re-captures the current label, tags, plan type, attached firewall(s), placement group, and watchdog setting before every stop, and replays them on the very next create, so a recreated instance looks and behaves identically in Cloud Manager and cost reports.

What does not survive, and has to be actively reproduced every single cycle, is anything Linode treats as belonging to the instance's own creation moment: its network configuration (which interface gets which address), its SSH host identity, and the instance ID itself (a brand-new one is assigned on every create). Parts 1.2 through 1.4 cover how each of those is handled.

1.2 Why the OS Has to Live on a Block Volume

A freshly deployed Linode instance normally gets its own local disk — fast, but tied to that specific instance, and gone the moment the instance is deleted. For a delete/recreate cycle to preserve the operating system and its data, the OS has to be moved onto a Block Storage volume instead, which is then attached fresh to each recreated instance at the same device slot every time.

Boot-from-volume carries a modest performance characteristic relative to local disk, which is why the standard approach — and the one this tool follows — is to build the OS disk locally once, as a golden template, then duplicate it onto a volume rather than installing directly onto Block Storage. Two onboarding paths follow directly from this: a brand-new instance can be provisioned straight from an already-prepared template volume (no migration needed, see Part II.1), while an existing instance already running on local disk needs a one-time migration to move its OS onto a volume before this tool can manage it (Part II.2).

Device order matters for every boot: the OS volume must always be attached at the first device slot, with any data volumes following in their original order, or the instance won't boot from the disk you expect.

1.3 The Two Networking Models

Linode instances use one of two mutually exclusive networking configurations — the older, config-attached interface model, and a newer model where interfaces are managed independently of any boot configuration, with explicit per-address NAT and default-route flags. An instance uses one or the other, never both, and the shape of a valid network configuration differs meaningfully between them (a public IP is delivered via a dedicated interface in one model, or via a NAT mapping with no separate public interface at all under the other).

This tool records which model a given instance actually uses at onboarding time, and reproduces the exact same model — and the exact same public-IP delivery topology — on every single recreate, never defaulting to one or silently translating between them. Getting this wrong for even one cycle would mean an instance that boots successfully but is unreachable, or reachable at the wrong address.

1.4 Staying Reachable at the Same Address, Every Time

A recreated instance needs to come back up already configured with the correct static IP, gateway, and subnet — not eventually, not after a manual fix, immediately on first boot.

Linode's own automatic network configuration writes a guest's network interface file once, the first time an instance boots on a given disk, based on whatever address that disk had at that moment. It does not re-run or self-correct when the same disk is later attached to a different instance with a different real address — which is exactly what happens on every recreate cycle, since the instance ID (and often the assigned interface) is new every time even though the disk and its intended address are unchanged.

The fix is to skip relying on that mechanism entirely for anything address-sensitive. At every create, this tool already knows the exact IP, gateway, and subnet each interface should have — it just captured them, or it's re-applying values fixed at onboarding — so it passes that configuration directly to the new instance via cloud-init, overwriting the guest's network files with the correct values before the network stack ever comes up, and restarting networking once they're in place. This runs on every single recreate, for every interface (public, VPC, and VLAN alike, when more than one is present), which is also why a multi-interface instance never ends up with more than one default route: every interface's configuration is stated explicitly, with nothing left to a default-assignment mechanism to guess at.

VPC and VLAN addresses specifically have to be explicit for the same underlying reason — Linode doesn't run address assignment on a VLAN interface at all, and a VPC's own automatic address assignment isn't guaranteed to hand back the same address on a later attachment, since a recreated instance gets a new hardware identity on every cycle.

1.5 SSH Host-Key Stability

An SSH client that connects to the same address twice and gets two different host keys back will refuse the second connection by design — the entire point of host-key checking is to detect exactly that. A naive recreate cycle would trigger this every single time, since cloud-init normally treats every new instance ID as a fresh machine and generates a brand-new host key on every boot.

This tool distinguishes two cases explicitly. The very first boot of a newly onboarded instance — a fresh clone of a golden template, or the first boot right after migrating an existing instance onto a volume — is allowed to generate a genuinely new key, since that's a real first-contact moment and every clone from the same template needs its own unique key, not a key shared across customers. Every steady-state recreate after that explicitly preserves the existing host key instead, so a managed instance presents the exact same SSH identity across every stop/start cycle, indefinitely.

If you deliberately need to rotate a host key Do it through the tool's own key-rotation command, never by editing its trust store by hand — see Part VI's CLI reference. A steady-state cycle presenting an unexpected key is treated as a genuine security event and refused outright rather than silently trusted; see Part VIII.
Part II

Onboarding

The two ways an instance comes under this tool's management — a fresh instance provisioned from a template, or an existing instance migrated in place — and what each one actually involves.

2.1 Path A — A Brand-New Instance

The simple path: there is no existing instance yet, so there's nothing to migrate.

A golden template — a Block Storage volume already holding a fully prepared OS image — is cloned directly into a new volume dedicated to this one logical instance. The clone is billed from the moment it succeeds, the same as any other volume, and happens exactly once, at onboarding — every later stop/start cycle attaches and detaches that same volume, it is never re-cloned. The new instance is then created against that volume, with a reserved public IP assigned to it (a fresh reservation, or one already held) and its VPC/VLAN addresses chosen once, at this point, never rechosen on a later cycle.

2.2 Path B — An Existing Instance

The path for an instance that's already running on ordinary local disk and needs its OS moved onto a Block Storage volume before this tool can manage it.

This is a real, one-time migration with genuine downtime, not a background operation — it needs a scheduled maintenance window. The sequence: a correctly sized destination volume is created, the instance is booted into Linode's Rescue Mode, and the actual disk contents are copied block-for-block from the local disk onto the new volume. That copy step is the one piece of this entire process that cannot be automated end to end: Rescue Mode has no API-level way to execute commands remotely, so it has to be run manually, once, inside Linode's interactive console (Lish). Everything before and after that single manual step — sizing and creating the destination volume, entering and exiting Rescue Mode, rebuilding the boot configuration against the new volume, verifying the copy actually took, and converting the instance's existing public IP to a reserved one in place (never swapped for a different address, since DNS and any external allow-lists already point at it) — is handled automatically.

Confirm device identity independently before copying The device letters this tool prints as a suggested copy command aren't guaranteed to match what the guest operating system actually sees for the source and destination disks. Before running the copy, independently list the guest's own block devices and match them by size to what's expected, rather than trusting the printed device letters as-is. Copying in the wrong direction is destructive and unrecoverable.

Two pre-flight conditions are checked before this process is allowed to start at all. First, a minimum cloud-init version with the correct metadata source has to already be present on the instance — the network re-injection mechanism in Part 1.4 depends on it, with no fallback, so an instance that doesn't meet this bar needs its cloud-init upgraded (or the OS itself upgraded to a release that ships a new-enough version) during the same maintenance window, before migration proceeds. Second, if the instance has hand-configured static networking outside Linode's own automatic configuration, that customization is flagged as a non-blocking warning — migration proceeds either way, but any such customization will be silently overwritten by the standard network re-injection on the very next recreate cycle, so it's worth knowing about in advance.

Existing data volumes attached to the instance need no migration at all — they were already independent of the instance's own lifecycle before this tool was ever involved. They're simply captured (which device slot they're in) and carried forward on every future cycle, exactly like a Path A instance's data volumes.

Part III

Scheduling

Individual and group schedules, how the two interact when an instance has both, and the poller that actually enforces them.

3.1 Individual and Group Schedules

A schedule is a set of rules — days of the week plus a start time and a stop time — attached either directly to one instance, or to a schedule group that several instances belong to.

An instance belongs to at most one group at a time. When both an individual schedule and a group are in play for the same instance, the rule is simple and absolute: an enabled individual schedule always wins outright, and the group's schedule is ignored entirely for that instance, not merged or blended with it in any way. Only when an instance has no enabled individual schedule of its own does its group's schedule take effect. An instance with neither is left under purely manual control — nothing is started or stopped automatically.

SituationWhat governs the instance
Has an enabled individual scheduleThat schedule, full stop — any group membership is ignored
No individual schedule, belongs to a groupThe group's schedule
No individual schedule, no groupManual control only, no automation

Removing an instance from a group never silently leaves it with no schedule at all — the choice is offered explicitly: keep it under purely manual control from that point on, or copy the group's current rules into a fresh individual schedule as a starting point.

3.2 Timezones

Every schedule — individual or group — is defined against a real IANA timezone name (for example America/New_York or Asia/Kolkata), never a fixed UTC offset. A fixed offset would silently drift by an hour across a daylight-saving transition; a named timezone resolves the correct wall-clock behavior automatically on both sides of that transition, with no special handling required from you. A group has exactly one timezone that every member following it inherits — an instance that needs a genuinely different timezone from the rest of its group is a signal that it should have its own individual schedule instead.

3.3 The Poller

A single long-running process evaluates every managed instance's effective schedule on a short, fixed interval, and fires a start or stop the moment a configured boundary is crossed. It matches against a small tolerance window rather than an exact instant, so ordinary timing drift between poll cycles never causes a scheduled action to be silently missed. Each action is recorded, so the same boundary is never fired twice in one day even if the poller restarts in between.

The poller is meant to run continuously under your own process supervisor (see Part IX.3 for a systemd example) — it doesn't need to be running for a manual start/stop to work, only for schedules and group memberships to actually be enforced automatically.

Part IV

Manual Control & Cost Visibility

What happens when you start or stop an instance yourself, outside its own schedule, and the two numbers this tool shows you for how much a schedule is actually saving.

4.1 Manual Override and Auto-Revert

Manual control and scheduled automation are meant to coexist, not fight each other.

Stopping an instance manually, at any time, needs no special handling — its schedule simply resumes normally at its own next configured boundary. Starting an instance manually outside its configured on-window is the case that needs a deliberate answer, because left alone forever it would silently erode the entire point of having a schedule. The behavior here: a manual start outside the schedule arms an automatic countdown, two hours by default, after which the instance is stopped again automatically unless you explicitly extend it. The countdown is shown plainly wherever the instance's status is displayed, and extending it is a single explicit action — it is never silently renewed on its own.

Instances with no schedule at all are never affected The auto-revert countdown only ever arms when a start happens outside an existing, configured schedule's on-window. An instance under purely manual control, with no schedule of any kind, can be started and left running indefinitely with no timer ever attached — that would work against the very point of deliberately choosing manual-only control.

4.2 Savings Shown as a Percentage, Not a Dollar Figure

Two numbers are shown for any instance or group with a configured schedule, and neither is a dollar estimate — contract and negotiated pricing aren't visible to this tool, so any dollar figure it produced would risk being flatly wrong for an account on a non-standard rate. Both are instead a percentage of a full week's hours avoided:

savings % = (1 − scheduled_hours / 168) × 100

Scheduled savings is computed purely from the configured schedule's own hours — visible the moment a schedule is set up, before it has ever run even once. Actual savings is computed retrospectively from real recorded uptime over a trailing window, and only becomes meaningful once a schedule has been in effect for a while. Shown together, the gap between the two is itself informative: a schedule configured for a high savings percentage that isn't being realized in practice is usually a sign that manual overrides are happening more often than the schedule intends.

Part V

Disaster Recovery

What happens if the local registry that tracks every managed instance is lost or corrupted — and the honest limits of how much of it can actually come back.

5.1 The Registry, and Why It Can Be Rebuilt From Nothing

Every managed instance's identity — which OS volume, which data volumes, which reserved IP, which schedule, which group — lives in one local database. Losing that file would normally mean losing the only record of which real Linode resources belong to which logical instance, with no way to reconstruct it.

This tool avoids that with two independent, layered backups, neither of which the local database ever depends on to function day to day. The first is Linode's own resource tags: the same identifying information is written directly onto the OS volume, each data volume, and the reserved IP themselves, every time an instance is onboarded or stopped. The second, optional layer is Object Storage: a single, complete backup of everything about the instance that tags can't hold, written to a bucket you control. The local database is always the fast, authoritative source of truth for day-to-day operation — recovery only ever reads from tags or Object Storage when that database itself is gone or unreadable, never otherwise.

Who answers "what's the truth" at any given moment The local database, without exception, whenever it's readable. Tags and Object Storage are never consulted during ordinary operation — not by the poller, not by a manual start or stop, not by the dashboard. They exist purely so the recovery command has somewhere to read from on the one occasion the local database itself is the thing that's broken.

5.2 What's Stored Where, and Why

Not everything about an instance is backed up the same way. Each piece of data goes wherever is cheap enough to be worth it, without ever pretending a size- and shape-constrained system like a resource tag can hold something it structurally can't.

Linode tags hold instance identity (which OS volume, which data volumes, which reserved IP), individual schedules, schedule-group membership and definitions, a simple single-network-interface configuration, and a reference to any SSH key that's also registered directly on the Linode account. Tags are free, visible directly in Cloud Manager, and survive independently of this tool's own database entirely — but each one is capped at fifty characters, a single resource can only hold a bounded number of them, and there is no way to write to more than one Linode resource at once as a single atomic operation. That combination makes tags the right home for small, fixed-shape facts, and the wrong one for anything of unpredictable size.

Object Storage, if configured, holds a single complete backup of everything else: a multi-interface or VPC/VLAN network configuration, an SSH key that isn't registered on the Linode account under any name, the instance's plan/firewall/placement-group/maintenance-policy/watchdog settings, its label, and its own Linode tags (the customer's own labeling tags, distinct from this tool's disaster-recovery tags). One plain record per instance, no size constraint, no bespoke encoding required — the tradeoff is that it's an optional layer a deployment has to explicitly set up, not something that exists automatically the way tags do.

Two things are recoverable through neither mechanism, both by deliberate choice, described fully in 5.6: a manual-override auto-revert timer that happens to be armed at the exact moment local state is lost, and the audit/history log. Both are explained there, including exactly what's actually at stake in each case.

5.3 Recovering a Stopped Instance

An instance that was genuinely running at the moment local state was lost recovers completely, always — everything about it, including its live network configuration and SSH access list, is simply read fresh off the running instance itself. A stopped instance has nothing live to read from, so it depends on what was captured and backed up the last time it was stopped or onboarded.

Recovery for a stopped instance follows a fixed order, and never guesses. First, the account is scanned for tagged resources by name — this is where identity comes from, always, and nothing later in the process ever overrides it. Second, the reserved IP's own tags are read for a schedule, group membership, and, if the instance's network configuration was simple enough to tag-encode, that configuration itself, plus a reference to any SSH key that's also a registered key on the Linode account — that reference is resolved back to the key's actual current content by looking it up on the account directly, not by trusting a stored copy. Third, if Object Storage is configured, the instance's full backup record is fetched and used to fill in whatever tags didn't already provide — a more complex network configuration, an SSH key with no account match, plan and firewall settings, label. Object Storage is consulted last and only ever fills a gap; it's never allowed to override what the tag scan already established for identity.

Once a network configuration and at least one SSH key are known — by any combination of the sources above — the instance is reported as fully recovered and ready to start normally, exactly like one that was running. If, after all of that, either is still missing, the instance comes back with its identity correctly restored but is flagged for the one remaining manual step: boot it once from its recorded volume and address, then hand it back to the tool the normal way.

5.4 Durable, Verified, Self-Healing Writes

Every stop or onboard writes the instance's newly captured state in two separate steps, to two independent systems — and those two steps are deliberately not, and cannot be, one atomic operation.

The local database write happens first, and it is real, immediate, and fully in effect the moment it succeeds — this is the one write every day-to-day operation of the tool actually depends on. The tag and Object Storage backups happen as a separate, second step, right after: each one is written, then read back and compared against what was just sent, and retried automatically on a transient failure. That verify-then-retry discipline exists because a write that appears to succeed isn't always trustworthy on its own — reading it back is the only way to be sure.

What isn't attempted is making the local write and the backup writes succeed or fail together. Two independent systems — a local file and a remote store — have no shared way to guarantee that; promising otherwise would be promising something this design can't actually deliver. What's guaranteed instead is durability without that guarantee mattering in practice: a backup failure never blocks or reverses the real operation (the local database write has already happened by the time a backup is even attempted), and it never needs to be manually tracked or retried, because the very next time that instance is stopped or onboarded again, its entire current state is backed up again from scratch. A single missed backup corrects itself on the next ordinary use of the instance — that's what "self-healing" means here: not that a failure is detected and repaired by some separate watcher process, but that the next routine write is always a full, current snapshot, never a partial update, so there's nothing stale left over to repair.

5.5 Recovering From a Corrupted or Lost Database File

A missing database file and a corrupted one are handled differently on purpose, because they mean different things.

A missing file is the easy case: the tool creates a fresh, empty database automatically the next time it runs, no special action needed at all beyond then running the recovery command described below. A genuinely corrupted file — present, but not a valid database — is detected specifically and distinguished from an ordinary momentary lock conflict between two processes; the tool refuses to proceed with a clear, direct message rather than behaving unpredictably against a file it can't actually trust.

Recovering from a corrupted database file Move the corrupted file aside (its exact location is named in the error message itself). Run the recovery command once. A fresh, empty database is created automatically, and the command reconstructs every managed instance's identity, individual schedule, and group membership from tags — plus, for any instance with a usable tag-based or Object Storage backup as described in 5.2–5.3, its full network configuration and SSH access too.

Nothing about this recovery path is destructive to the real infrastructure it's recovering the record of — the instances, volumes, and reserved IPs it reconstructs a registry entry for were never touched by the loss of the local file in the first place. The recovery command only ever reads and reconstructs; it never deletes or recreates anything on the Linode side as part of this process.

5.6 Edge Cases, and What's Actually at Risk in Each

Most of what could theoretically go wrong here turns out not to matter in practice, because the design already accounts for it. The genuine edge cases are narrow, and worth stating plainly rather than leaving implicit.

SituationWhat actually happens

The next successful stop or onboard for that same instance re-attempts the backup with its then-current state. The only actual exposure is a total local database loss landing in the narrow window before that next backup succeeds, in which case recovery falls back to whatever the last successful backup provided.
Both the tag and the Object Storage backup happen to disagreeTags win, for the fields tags cover. Both are written at the same moment from the same captured state, so in practice they only ever disagree if one of the two most recent write attempts failed while the other succeeded — not a routine occurrence.

7.2 Authentication: Two Credentials, Two Jobs

The API supports "Login with Linode" — your team signs in with the exact same account credentials they already use for Cloud Manager, rather than a separate shared secret.

This login token answers exactly one question — who is calling right now — and is never used to talk to Linode's own API directly. A completely separate, full-access Linode API token, configured once by whoever deploys the tool, is what actually performs every real operation. This separation is deliberate: the scheduler has to keep running and firing scheduled actions even when nobody is logged in, which only works if the credential doing the real work isn't tied to any one person's login session.

7.3 The Web Dashboard

A browser-based dashboard, served by the same API process, covers the full day-to-day surface: signing in, viewing and onboarding instances, configuring individual and group schedules, starting and stopping instances manually (with the auto-revert countdown shown plainly when active), managing group membership, and both savings percentages. It's a thin visual layer over the identical API described above — nothing it does isn't equally available from the CLI.

Part VIII

Security

How SSH access, host-key trust, and the two credential types are handled.

8.1 One SSH Keypair, Never a Stored Credential

SSH access is needed on an ongoing basis — to verify real reachability after every recreate, and to re-read the current authorized-keys list before every stop so a departing team member's revoked access isn't silently reinstated on the next cycle.

This never requires storing a customer's root credential anywhere. One SSH keypair belongs to the deployment itself — its private key lives only on the server running this tool, read fresh at each use, never written into the database. For a brand-new instance provisioned from a template, this deployment's public key is simply baked into the template once, with no credential ever exchanged. For an existing instance being brought under management, you add this deployment's public key yourself, the normal way you'd add any key — through access you already have.

A one-time fallback exists on the onboarding screen for a customer who'd rather hand over temporary access than add the key themselves — a password or a private key pasted directly into the form. Neither is ever written to the database: a pasted password is used once, for that single request, and discarded; a pasted private key is written to a locked-down temporary file, used once, and deleted immediately afterward regardless of whether onboarding succeeds or fails.

8.2 Host-Key Trust Fails Closed

Every steady-state reachability check verifies the presented SSH host key strictly against the one recorded for that instance (see Part I.5) — a mismatch is refused outright, exactly the way an ordinary SSH client would refuse it, rather than silently accepted. A genuinely new host key is only ever trusted at a deliberate first-contact moment (initial onboarding, or an explicit, operator-run key rotation) — never automatically during ordinary operation.

Part IX

Deployment Model

Who runs this, on what, and why the design choices fit that model.

9.1 Self-Hosted, One Deployment Per Account

This is a tool you run yourself, against your own Linode account — not a shared service operated on your behalf.

Every design choice downstream of this follows from it. The local registry is a single SQLite database file — no separate database server to stand up, secure, or back up, appropriate for a single-tenant, self-hosted deployment where the alternative (a full relational database server per customer) would be a heavy, unjustified operational ask for what's meant to stay a lightweight tool. If you register a dashboard login, it's your own OAuth application registered in your own Linode account — there is no shared vendor infrastructure of any kind in the credential path.

9.2 High Availability, the Appropriate Way for This Workload

This tool's availability model is built around fast, safe recovery rather than redundant, always-on replicas — a deliberate choice, not the absence of one.

An active-active setup (two or more scheduler processes running at once) and an active-passive setup (a hot standby ready to take over) both solve the same underlying problem: keeping a system reachable and correct through the brief window while one instance of it is down. Neither problem actually exists here in a way that justifies the cost of solving it. The scheduler's whole job is to notice a scheduled boundary has been crossed and fire a start or stop — it evaluates on a short, fixed interval with a tolerant matching window (typically a few minutes either side), not on every incoming request the way a system serving live traffic does. If the process is briefly down — a crash, a host reboot, a deploy — the next scheduled action simply fires a few seconds late, once an ordinary process supervisor brings it back up; nothing downstream notices or breaks, since nothing downstream is waiting on it in real time. Manual control (the CLI and, if you run it, the REST API and dashboard) works independently of the scheduler the entire time regardless — an operator is never blocked from starting or stopping a node by hand just because the scheduler happens to be restarting.

Active-active would trade that brief, harmless delay for a real correctness risk instead: two scheduler processes with no genuine coordination between them (a distributed lock, a leader election, a consensus protocol — the actual infrastructure "active-active" implies) could both decide the same instance is due for the same action at the same moment and race each other, or worse, one could fire a start while the other is mid-firing a stop for the same node. That's a new failure mode this tool would be introducing to solve a problem — a few seconds of scheduler downtime — that a plain restart already solves for free. Active-passive avoids the double-fire risk but still needs its own machinery to be worth anything: health checks to detect the primary is actually down (not just slow), a way for the standby to agree it should now be the one acting, and a shared or replicated view of state so the standby doesn't start from a blank slate. All of that is real, ongoing infrastructure with its own failure modes, kept running and paid for at all times, to protect against an outage that a single supervised process already recovers from in the time it takes to restart.

This is also, directly, a cost decision, not just an architectural one. This whole product exists to eliminate paying for compute that isn't earning its keep — running a second, always-on scheduler instance (active-passive) or two simultaneously-active ones (active-active) purely as insurance against a multi-second restart would mean paying for exactly the kind of idle, always-on capacity this tool is built to help you stop paying for, just moved from your managed fleet onto the tool's own infrastructure instead. The model actually used costs nothing extra to run: one process, under whatever process supervisor already ships with the host operating system, on the one machine you're already running this from.

Three layers make up the actual model, from most to least commonly needed: a process supervisor restarts the scheduler automatically if it ever crashes (9.3, below); a simple periodic file copy of the local database, plus the tag and Object Storage backups described in Part V, make a routine restore fast; and if even the local file itself is gone, the tag-based reconstruction described there is the guaranteed fallback of last resort. Deliberately absent, at every layer, is a second, simultaneously active scheduler process.

9.3 Installing and Configuring

A self-hosted tool means there's a genuine install step — brief, and the same on every deployment.

The tool is a plain Python program with no database server, no message queue, and no other infrastructure of its own to stand up. Cloning the repository, creating a virtual environment, and installing its dependencies is the entire installation:

StepWhat it does
git cloneGets the code — run this on the one centralized, persistent machine your whole team will use, not a personal laptop (see 9.1).
python3 -m venv .venv && source .venv/bin/activateAn isolated Python environment, so this tool's own dependencies never conflict with anything else on the host.
pip install -r requirements.txtInstalls everything the tool needs to run.
cp .env.example .envCreates your own local configuration file — already excluded from version control, since it's about to hold a real credential.

Configuration is one flat file, .env, read once at process startup. Exactly one setting is required to run anything at all — a full-access Linode Personal Access Token, since this tool creates, deletes, and tags real Linode resources on your behalf. Everything else is optional, and each piece only matters if you're using the specific feature it enables:

reserved IP
A public IPv4 address held independently of any instance, so it survives that instance being deleted and can be reattached to whatever's recreated in its place. Permanently locked to the region it was first reserved in; carries a small charge while unattached.
golden template / template volume

rebuild
